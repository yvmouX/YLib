# 生命周期（Lifecycle）

YLib 自己**不接管你的插件生命周期**：`YLib.init(this)` 只是装配库的各个子系统（日志、消息、配置、命令、菜单），
之后什么时候加载配置、什么时候重载、什么时候关停，都由你的 `onEnable` / `onDisable` 决定。
这篇把「一次加载里 YLib 内部按什么顺序做了什么」讲清楚——排查「配置没生效」「注释没写进文件」
「重载后值没变」这类问题时，照这里对照就行。

## 全貌

```text
onEnable
   │
   ├─ YLib.init(plugin)                    ← 装配库（必须最先）
   │     · 探测服务端类型（Spigot / Paper / Folia / Canvas）
   │     · 创建日志器、配置管理器、命令管理器
   │     · 调度器按需创建（第一次 getScheduler() 时才定实现）
   │
   ├─ registerConfiguration(Xxx.class)     ← 加载一份配置，内部有 5 步（见下）
   │     每份配置独立走一遍，互不影响
   │
   └─ 你自己的后续装配（数据库、引擎、监听器、命令…）

onDisable
   │
   └─ 自行关停（YLib 没有 shutdown 钩子）
         逆序来：先停定时器 → 再注销监听器 → 最后关库
```

`YLib.init` 是**单例**：第二个插件调用它，如果插件实例不同会直接抛 `YLibException`，
而不是静默复用——服务都绑在首个初始化的插件上，复用会让命令与配置挂到错误的插件上。

## `registerConfiguration` 的五步

这是最需要搞清楚的一段——**配置的「加载」不是一次读文件，而是五个步骤按固定顺序跑**：

| # | 步骤 | 做什么 | 文件不存在时 | 什么情况下会**写文件** |
|---|---|---|---|---|
| 1 | `checkVersionAndMigrate` | 比对 `config-version` 与注解里的 `version` | 直接返回（交给第 2 步） | 版本不一致：**备份旧文件 → 重新生成 → 迁移旧值** |
| 2 | `generateDefault` | 生成带默认值与注释的文件 | 走这里 | 文件不存在时创建 |
| 3 | `mergeMissingKeys` | 补齐缺失的键；刷新标了 `refreshComment` 的注释 | 直接返回 | 有键缺失、或有注释需要刷新时 |
| 4 | `load` | 把文件里的值塞进字段 | 直接返回（字段保持 Java 默认值） | 不写 |
| 5 | `validate` | 跑 `required` 与 `validation` 规则 | — | 不写；不通过**抛异常** |

两个容易踩的点：

- **第 5 步失败会抛异常**，不是记日志。你的 `registerConfiguration` 调用点要么让它冒到
  `onEnable` 顶层（插件直接报错），要么自己 `try/catch` 决定降级——YLib 不替你做这个决定。
- **第 3 步与第 1 步都会写文件**，且第 1 步的写入最"重"（备份 + 重建）：改 `version` 要清楚它会
  把用户文件里**所有**手写内容（注释、分组、键顺序）重置一遍，只有值会被迁移回去。

## 注释的写入与刷新

注释能力是 Bukkit 提供的（`setComments` / `getComments`，**Spigot 1.18.1+**），YLib 用反射调，
低版本上**读写都静默失效**（不报错、也不会有注释）。

| 时机 | 注释怎么处理 |
|---|---|
| 第 2 步生成文件 | 每个字段按 `description` 写注释（`\n` 会拆成多行） |
| 第 3 步补齐缺失键 | 新补的键写 `description` |
| 第 3 步（`refreshComment = true` 的字段） | 每次加载都按 `description` 重写，**除非**注释里有 `@keep` |
| 第 1 步版本迁移 | 文件重建，注释全部按 `description` 重来（`@keep` 也保不住，去备份里找） |

`refreshComment` 默认 `false`，即「键已存在时不动注释」——这是不打扰用户的默认值；
标 `true` 才让说明跟着代码走。细节见 [配置文档](配置.md#注释)。

## 重载（`reloadConfiguration`）

`reloadConfiguration(Class)` 比首次加载**少做不少事**——它只跑两步：

```text
reloadConfiguration(Xxx.class)
   ├─ 克隆一份旧值（校验失败时用来回滚）
   ├─ load      ← 只读值，不写文件
   ├─ validate  ← 不通过就回滚到旧值并返回 false
   └─ 通知监听器
```

**不跑**的三步及后果（这是最容易踩的地方）：

| 不跑的步骤 | 后果 |
|---|---|
| `checkVersionAndMigrate` | 改 `version` 注解后，**重载不会触发迁移**；要重启才生效 |
| `generateDefault` | 文件被删了，重载不会重新生成 |
| `mergeMissingKeys` | **重载不会补缺失的键，也不会刷新注释**——`refreshComment` 只在启动（首次注册）时生效 |

> 也就是说「注释每次加载都刷新」里的**「每次加载」= 每次启动**，不含 `/reload` 这类热重载。
> 想让重载也刷新注释，得自己在重载后调一次配置管理器的 `mergeMissingKeys`（或等价入口）。

其他与首次加载的区别：

- **失败会回滚**，返回 `false`；首次加载失败是抛异常。所以重载的调用点应该检查返回值——
  典型写法是「任一份失败就报给执行命令的人」，而不是静默继续。
- 重载**不会**重新注册监听器、不会重启调度器、不会重连数据库。它只管把**配置值**换掉；
  依赖配置的东西要不要跟着重建，由你的调用点决定。

## 与 YLib 其他部分的时序关系

| 子系统 | 什么时候初始化 | 说明 |
|---|---|---|
| 日志器 | `YLib.init` | 立即创建 |
| 配置管理器 | `YLib.init` | 立即创建，但里面是空的，等 `registerConfiguration` 往里注册 |
| 命令管理器 | `YLib.init` | 立即创建，命令由你的命令类注册进去 |
| 调度器 | 首次 `getScheduler()` | 懒创建，按服务端类型选实现（Folia / Canvas 用各自的区域调度器） |
| 消息服务 | 首次注册时 | 懒创建；**首个**注册的实例被缓存，`getMessageService()` 拿到的就是它 |
| 菜单监听器 | 首次用菜单时 | 不在 `YLib.init` 里；`MenuListener.init(plugin)` 由使用方触发，只需一次 |

顺序上的硬约束只有一条：**`YLib.init(plugin)` 必须最先**——日志器、配置管理器、命令管理器都在它里面创建。
`registerConfiguration` 要在 `YLib.init` 之后、用到配置值之前。

> 「懒创建」这几个的副作用：**如果你从不调用它们，它们就从不初始化**。
> 排查「某某服务没生效」时先确认自己是否真的触发过它的创建路径。

## 关停

YLib **不提供 `shutdown`**，也不持有需要显式释放的资源（配置与语言文件都是读进内存后就结束）。
你在 `onDisable` 里要关的是**自己的东西**，顺序上注意：

```java
@Override
public void onDisable() {
    scheduledTasks.shutdown();      // 1. 先停定时器——它可能在异步线程里碰数据库
    HandlerList.unregisterAll(this); // 2. 再注销监听器
    storage.close();                 // 3. 最后关库，避免「连接已关闭」的报错
}
```

这个顺序不是 YLib 要求的，而是「谁依赖谁」的直接推论：定时器依赖库、监听器依赖库，
所以库最后关。倒过来写就会出现「关库之后定时器又触发一次」这类只在关服时冒出来的错误。
